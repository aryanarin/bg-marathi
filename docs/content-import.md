# Content import

How scripture content gets from a source text into the database.

The pipeline is deliberately two-step: **validate**, then **import**. Malformed
content is rejected loudly rather than imported silently, because bad scripture
data is much harder to notice and undo than a failed script run.

```
content/chapter-01.json
        │
        ├─ npm run content:validate   ← read-only, no database
        │     strict schema check, duplicate detection, warnings
        │
        └─ npm run content:import     ← writes to Supabase (Phase 4)
              upsert by (chapter_number) and (chapter_id, verse_number)
```

## A rule I follow

**I do not invent scripture.** Verse text, word-to-word meanings, translations
and purports are copied from a source edition you provide. If content is
missing, I leave the field absent and report it, rather than generating
plausible-sounding text. Generated scripture would be worse than no scripture.

The two fields the administrator authors — `easy_explanation` and `example` —
are likewise never generated by me or by the application.

## File format

One file per chapter, at the repository root in `content/`:

```
content/
├── chapter-01.json
├── chapter-02.json
└── ...
```

The filename must agree with `chapter_number` inside the file. The validator
enforces this, because a mismatch would silently write to the wrong chapter.

```json
{
  "chapter_number": 1,
  "name_sanskrit": "अर्जुनविषादयोग",
  "name_marathi": "अर्जुनाचा विषाद",
  "description": "कुरुक्षेत्राच्या रणांगणावर अर्जुनाला झालेला मोह आणि विषाद.",
  "verses": [
    {
      "verse_number": 1,
      "sanskrit_text": "धर्मक्षेत्रे कुरुक्षेत्रे समवेता युयुत्सवः ।\nमामकाः पाण्डवाश्चैव किमकुर्वत सञ्जय ॥",
      "word_to_word": "धर्मक्षेत्रे — पवित्र धर्मभूमीवर; कुरुक्षेत्रे — कुरुक्षेत्रावर; समवेताः — एकत्र आलेले",
      "translation": "धृतराष्ट्र म्हणाला: हे संजया! धर्मभूमी कुरुक्षेत्रावर युद्धाच्या इच्छेने एकत्र जमलेल्या माझ्या आणि पांडूच्या पुत्रांनी काय केले?",
      "purport": "धृतराष्ट्र जन्मांध होता आणि आपल्या पुत्रांबद्दल अत्यंत मोहग्रस्त होता…",
      "easy_explanation": "",
      "example": "",
      "audio_url": "",
      "audio_provider": "supabase_storage"
    }
  ]
}
```

### Field reference

| Field | Required | Notes |
| ----- | -------- | ----- |
| `chapter_number` | Yes | Integer 1–18. Must match the filename. |
| `name_sanskrit` | Yes | Non-empty. |
| `name_marathi` | Yes | Non-empty. |
| `description` | No | Chapter summary. |
| `verses` | Yes | At least one verse. |
| `verse_number` | Yes | Integer ≥ 1, unique within the chapter. |
| `sanskrit_text` | Yes | **Must contain Devanagari characters.** Use `\n` for line breaks. |
| `word_to_word` | Yes | Non-empty. |
| `translation` | Yes | Non-empty. |
| `purport` | Yes | Non-empty. |
| `easy_explanation` | No | **Administrator-authored.** Empty string or omitted is fine. |
| `example` | No | **Administrator-authored.** Empty string or omitted is fine. |
| `audio_url` | No | Empty string, or an `https://` URL. |
| `audio_provider` | No | One of `supabase_storage`, `google_drive`, `external`. |

Unknown keys are **rejected**. This catches typos like `tranlsation`, which
would otherwise import as a missing field.

Whitespace-only values are rejected for required fields, since a pasted-but-empty
cell is a common data-entry error.

`sanskrit_text` must actually contain Devanagari. A transliterated or
English-only value there is a content error, not a stylistic choice.

## Validating

```bash
cd web
npm run content:validate            # all chapters
npm run content:validate -- 01      # one chapter
npm run content:validate -- 1 2 3   # several
```

Exits non-zero on any error, so it can gate CI or a pre-import check. It only
reads files and never touches the database.

Sample output:

```
PASS  chapter-01.json  47 verses
      warn   12 of 47 verses have no audio_url
      warn   47 of 47 verses have no easy_explanation (admin-authored, can be added later)

FAIL  chapter-02.json  2 error(s)
      error  verses.4.translation: translation रिकामे असू शकत नाही / must not be empty
      error  verses.17.verse_number: Duplicate verse_number 17 (also at verses[16])
```

### Errors vs warnings

**Errors** block import:

- Invalid JSON
- Missing or empty required field
- `sanskrit_text` with no Devanagari
- Duplicate `verse_number` within a chapter
- `chapter_number` outside 1–18
- Filename not matching `chapter_number`
- Unknown keys
- Non-`https` `audio_url`

**Warnings** are informational and do not block:

- Gaps in verse numbering — legitimate for a partial import, and the source text
  does combine some verses (e.g. "16–18")
- Missing `audio_url`
- Missing `easy_explanation`
- `audio_url` present with no `audio_provider`

## Importing — [Phase 4]

The import script is not written yet. Its behaviour will be:

```bash
cd web
npm run content:import -- 01        # one chapter
npm run content:import -- --all     # everything
npm run content:import -- 01 --dry-run
```

- Validates first and refuses to run if validation fails.
- Uses the **service-role key**, because there is no user session in a CLI
  script. This is one of only two legitimate uses of that key.
- **Upserts** on `chapter_number` and on `(chapter_id, verse_number)`, so
  re-running is safe and idempotent. Re-import after a correction updates rows
  rather than duplicating them.
- Never deletes. Removing a verse is a deliberate manual action.
- Sets `display_order` from `verse_number`.

`--dry-run` will report what would change without writing.

## Audio hosting — open decision

Audio lives outside the application. Each verse stores `audio_url` and
`audio_provider`, and the player treats the URL as opaque external media.

### Why Google Drive links will not work directly

Your files are at a public Drive folder, but a Drive **share link cannot be used
as an `<audio src>`**:

- `drive.google.com/file/d/ID/view` returns an HTML viewer page, not audio bytes.
- The `uc?export=download&id=ID` workaround is rate-limited, serves a virus-scan
  interstitial for larger files, and Google has been progressively restricting
  it. It also sends no `Accept-Ranges`, so **seeking within a verse will not
  work**.
- It fails most often on mobile Safari, which is a primary target here.

This is not a "might break later" concern; it breaks in normal use.

### Recommended: Supabase Storage

You already have Supabase. Storage gives a real CDN with correct `Content-Type`
and range requests, the free tier includes 1 GB (ample for ~700 short MP3s), and
it adds no new vendor. Per the brief's "no unnecessary external services", this
*removes* a dependency rather than adding one.

**[YOU]** if you choose this:

1. Supabase Dashboard → **Storage** → **New bucket**
2. Name: `verse-audio`
3. **Public bucket: ON** — audio is not secret, and public access avoids signed
   URLs expiring mid-playback
4. Upload files as `chapter-01/verse-001.mp3`, `chapter-01/verse-002.mp3`, …

Public URLs then look like:

```
https://<ref>.supabase.co/storage/v1/object/public/verse-audio/chapter-01/verse-001.mp3
```

Which is a predictable pattern, so I can generate every `audio_url` from the
chapter and verse number instead of you pasting 700 links.

**Send me:** the bucket name and one working public URL, and I will write the
URL generator.
